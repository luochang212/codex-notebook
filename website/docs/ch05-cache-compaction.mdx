下午两点，你开始让 Codex 重构一个认证模块。它读了 12 个文件，改了 5 个，跑了 3 次测试，修了 2 个 bug。到下午四点，你已经和它来回聊了 40 多轮。

这时候发生了一件你看不见的事：context window 快满了。

128K token 的窗口，听起来很大。但 40 轮对话里，每轮包含模型输出、工具调用、工具结果、环境信息 diff……累积下来，已经用了 110K。还剩 18K。而模型下一次响应可能就需要 5K。再跑两个工具调用，就爆了。

系统必须做点什么。但它不能简单地砍掉旧消息——那会让模型忘记自己改过哪些文件、为什么改、测试跑到哪了。

## 压缩不是截断，是换窗

Codex 的做法是：把当前全部对话历史发给模型，让它写一段摘要。然后用这段摘要**替换**整个历史。

不是截断前 N 条消息。不是只保留最近 K 轮。是让模型自己总结："我做了什么、为什么做、当前状态是什么、下一步计划是什么"。然后旧历史消失，摘要成为新的起点。

压缩后保留什么：

- canonical initial context（重新建立的底版）
- 最近的多条用户消息（从后向前按 token 预算保留，必要时截断一条）
- 摘要文本（模型生成的）

丢弃什么：所有中间 tool call 和 tool result、所有中间推理过程、旧的 context diff 序列。

注意：模型可见的 active history 被替换了，但持久化的 rollout 文件不会物理删除旧记录。它追加一个 `RolloutItem::Compacted`，其中保存了 replacement history。恢复时按它重建。

## 压缩发生在 turn 中间，不打断你

这是最巧妙的设计：压缩不需要用户参与。它有两个触发点：Turn 循环内部（模型调完一次工具后，系统检查 token 用量，超限就地压缩），以及首次采样前（`run_pre_sampling_compact`，如果上一步留下的窗口已经接近上限，先压缩再采样）。

用户看到的是什么？一条警告："长线程和多次压缩可能降低准确性，建议开新线程。"然后模型继续干活。它不会说"上下文快满了，我来压缩一下"。它只是继续。

## 压缩没有换 key，但改写了可匹配前缀

这里有一个隐性成本，和 ch04 直接相关。先说一个容易混淆的事实：**compaction 不会给 session 换一个新的 `prompt_cache_key`。**普通 Responses 请求默认使用 session ID 作为 key，远程 compaction 请求也从同一套请求构造逻辑中取出并继续发送这个 key。

变化的是 key 所对应的 prompt 内容。压缩前，请求携带原始历史：用户消息、模型回复、tool call、tool result 和逐步追加的 context diff。压缩后，active history 被 replacement history 取代：旧控制流不再逐项出现，摘要和保留下来的用户消息成为新的会话主体。即使 key 相同，缓存断点处的精确前缀也已经不同。

所以不能简单地说“压缩把缓存清空了”。Codex 客户端没有权限清空推理服务器上的 KV cache，旧条目也可能仍在保留期内。准确的说法是：**压缩改写了下一次请求用于匹配的前缀，旧缓存对新请求通常不再直接适用。**具体命中多少，取决于服务端的 breakpoint、路由、保留时间和淘汰状态。

新的 canonical initial context 和 world state baseline 建立后，后续 diff 仍然只向尾部追加，系统重新获得一个稳定前缀。这里的取舍不是“是否保住同一 cache key”，而是“是否保住旧历史的逐项结构”：Codex 放弃后者，换取足够小且内部一致的新窗口。

如果强行只从头部删除若干消息，确实可能暂时少生成一段摘要，但模型拿到的会是一条缺少因果起点的工具执行链。某个 tool result 可能还在，它对应的 tool call 却已经被删掉；某项修改仍被后文引用，做出修改的约束却消失了。Codex 宁愿承担新前缀的 prefill 成本，也不把这种结构断裂交给模型继续猜。

## 缓存和记忆解决的不是同一个问题

Prompt cache 容易让人误以为系统“已经记住了旧对话”。实际上，KV cache 只是一次前向计算的中间结果；它减少重复计算，却不决定哪些事实进入模型当前可见的语义上下文。即使旧 KV 条目仍存在，只要新请求的缓存条件不匹配，模型就无法借此恢复被 compaction 删除的细节。

Compaction 做的恰恰相反：它不追求无损保存计算状态，而是重新编码语义。旧历史中的几十条消息被压成一段摘要，计算上需要形成新的缓存前缀，语义上却尽量保留“接下来还需要知道什么”。因此两者的失败方式也不同：

- cache miss 的后果是多做 prefill、增加延迟或费用，模型仍然能看到完整输入；
- compaction 遗漏的后果是事实从 active history 中消失，后续模型可能据此做错决定。

这解释了为什么 Codex 会分别记录两类信息。`TokenUsage` 中的 `cached_input_tokens` 和 `cache_write_input_tokens` 用来观察计算复用；`RolloutItem::Compacted` 和 replacement history 用来恢复压缩后的语义状态。前者是性能账，后者才是会话记忆账。

## 摘要质量是软肋

这套机制有一个无法用工程解决的弱点：摘要质量取决于模型。

如果模型写了一段很好的摘要——关键决策、文件变更、未完成任务都记下来了——后续行为几乎不受影响。但如果摘要写得差——漏掉了"用户说过不要动 auth 模块"这个约束——后续模型可能就会去动 auth 模块。

这是一个有损操作，而且损失不可预测。没有"压缩后验证摘要完整性"的机制。压缩完就完了，模型基于摘要继续工作。

## 两种压缩路径

Codex 支持本地压缩和远程压缩：

- **本地**：用当前模型做摘要，消耗本地 token budget
- **远程**：provider 支持时，压缩在服务端完成。客户端仍记录这次调用的 token usage，但具体计费策略由产品决定

远程压缩的优势是由 provider 的专用 endpoint 完成历史压缩，但不是所有 provider 都支持。它仍然要接收待压缩的输入，也可能产生 cached input 和 cache write usage；“远程”描述的是执行位置和接口，不代表这次操作没有上下文计算成本。

## 回到那个下午四点

你的 session 在压缩后继续运行。模型看到的是重建的初始上下文、最近几条用户消息和一段摘要，而不是 110K token 的完整历史。它知道自己改过哪些文件、测试状态如何、下一步要做什么。但它不再记得第 7 轮时你说过的一句随口评论，也不再记得第 15 轮时它尝试过但放弃的一个方案。

这是有意的。那些细节在当时的上下文里有意义，但对"接下来做什么"已经不重要了。如果它们真的重要，摘要会记住。如果不重要，忘了就忘了。

对话可以延续很久。代价是：越远的记忆越模糊，而且源码主动警告：多次压缩会降低模型准确性。如果任务允许，开新线程比无限续跑更可靠。就像人一样——睡眠不足时记忆力下降，你知道该休息了。
